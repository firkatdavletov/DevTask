# dev-task

`dev-task` планирует и выполняет задачу из локальной карточки в отдельном Git worktree,
проверяет результат командами проекта и запускает code review в новой сессии
Codex. После успешных checks и review он может создать коммит, отправить ветку и
открыть Draft PR. Для локальной работы используйте `--local-only`.

Требуются Python 3.10+, PyYAML (`python3 -m pip install -r requirements.txt`),
Git, авторизованный Codex CLI и GitHub CLI `gh`. Рабочие каталоги и журналы
задаются в `config.json` и должны находиться вне checkout приложения.

## Карточка и модели

Карточка начинается с YAML. Обязательны `issue`, `base`, `title`, `complexity`
и непустое описание. Поддерживаются номера `APP-1234` и `SS-5678`; `base` —
`develop` либо другая ветка `feature/APP-1234` или `feature/SS-5678`.
Регистр сложности нормализуется.

```yaml
---
issue: APP-1234
base: develop
title: Редактирование имени пользователя
complexity: medium
---

Опишите поведение и критерии приёмки.
```

| Сложность | Planning | Coding и исправления | Review |
| --- | --- | --- | --- |
| `trivial` | пропуск | luna / low | пропуск |
| `simple` | пропуск | luna / medium | sol / low |
| `medium` | sol / medium | sol / medium | astra / low |
| `complex` | astra / high | sol / high | astra / medium |

По умолчанию `luna=gpt-6-luna`, `sol=gpt-6.1-sol`, `astra=gpt-6-astra`.
Настройте соответствия в `models`, а целый профиль этапа — в
`complexity_profiles`. Для planning и review можно указать `null`. Coding обязателен.
Недоступная модель не подменяется другой. `codex_args` поддерживает совместимые
флаги CLI, в том числе `--add-dir` для coding; конфликтующие настройки модели,
глубины и sandbox отклоняются. Planning и review работают в sandbox `read-only` и не
получает дополнительные каталоги для записи.

## Запуск

```bash
./dev-task run android-tasks/APP-1/task.md --config config.json --local-only
```

Порядок: подготовка worktree → setup → planning → coding → checks → review. Каждый вызов
Codex запускается в новой сессии. Coding и исправления работают в
`workspace-write`. Проверки выполняются командами `checks` из `config.json`.
После проверки Git index и исходников review получает полный diff относительно
исходного commit, карточку, результаты и журналы checks.

Планировщик изучает карточку, проект и текущий diff. Он возвращает структурированный
план изменений и проверок критериев приёмки. Скрипт сохраняет его в
`attempt-*/planning-N/plan.md` вне worktree и передаёт путь coding, review и всем
исправляющим сессиям. Ошибка, blocker или неверный результат planning останавливают
работу до coding. Планировщик не должен менять исходники, новые файлы, права,
индекс, ветку или HEAD; скрипт проверяет это и после ошибки/прерывания.

`run --skip-planning` пропускает planning дополнительно к профилю. Причина
сохраняется между обычными запусками; сменить режим можно через `--rerun`.
Успешные setup и planning при продолжении не повторяются. В циклах исправлений
планировщик заново не запускается. Принятый план неизменяем внутри цикла:
если `plan.md` потерян или изменён, нужен новый цикл `run --rerun` до коммита.

На `trivial` review пропускается. Для отдельного запуска можно передать
`run --skip-review`; причина пропуска сохраняется в состоянии задачи и действует
при последующих `run` без флага. Чтобы изменить режим пропуска, сложность,
модель или глубину до коммита, используйте `run --rerun`.

Если checks завершились ошибкой, `dev-task` запускает исправляющую сессию с
полными журналами, затем повторяет все checks. Лимит
`max_check_fix_iterations` по умолчанию равен `3`; `0` отключает эту возможность.
Ошибка setup, нарушение допустимых путей, изменение ветки/HEAD или изменение
исходников самими checks останавливают работу.

Замечания review P0/P1/P2 запускают отдельный цикл: исправление → все checks →
новое review. Настройка `max_fix_iterations` по умолчанию `3`; `0` отключает
автоисправление review. P3 сохраняются без обязательного исправления. Оба лимита
отдельны; ошибка, таймаут или прерывание исправляющей сессии расходуют попытку.
Оставшиеся P0/P1/P2 не допускают публикацию.

После локального запуска и просмотра diff опубликуйте тот же проверенный снимок:

```bash
./dev-task publish android-tasks/APP-1/task.md --config config.json
```

Команда `run` без `--local-only` публикует сразу после успешных checks и review.
`publish` повторяет checks и сверяет сохранённое review с текущим Git-снимком.
Если код изменился, выполните `run`, чтобы получить актуальное review.
Повторная публикация переиспользует коммит и существующий Draft PR.

Перед созданием коммита отдельная сессия luna (`models.luna`, по умолчанию
`gpt-6-luna`, глубина `low`, sandbox `read-only`) составляет краткое сообщение
на русском по проверенному diff. Скрипт добавляет только номер Jira:
`KRMA-10003 Добавил обработку ошибки на экране подачи`, без суффикса имени задачи.
Сообщение сохраняется в состоянии и переиспользуется после ошибки коммита;
изменение проверенного кода вызывает новую генерацию. Ошибка модели или неверный
формат останавливают публикацию. Журналы и расход доступны в отчёте как
«Сообщение коммита». Уже созданные коммиты сохраняют прежнее сообщение.

## Продолжение и отчёт

Для доработки опубликованного Draft PR обновите карточку и выполните:

```bash
python3 ./dev-task run android-tasks/KRMA-10003-add-username-validation-error/task.md --config config.json --continue-pr
```

Новый цикл сохраняет незакоммиченные правки в существующем worktree и проходит
setup, planning, coding, checks и review по выбранному профилю. Новый коммит
отправляется в ту же ветку; номер, заголовок и описание PR сохраняются.
Review проверяет полный PR, а luna описывает только текущую доработку.
Если изменений кода нет, пустой коммит не создаётся.

`--continue-pr` совместим с `--local-only`, `--skip-planning`, `--skip-review`.
После `--local-only` выполните обычный `publish`. После ошибки повторите `run`
или `run --continue-pr`: незавершённый цикл продолжится без сброса попыток.
После ошибки push используйте `publish`: уже созданный коммит переиспользуется.
Нельзя одновременно передавать `--continue-pr` и `--rerun`. Если карточка меняется
в активном цикле до коммита, используйте `run --rerun`. После коммита сначала
завершите публикацию. Поля `issue` и `base` должны оставаться прежними.

Продолжение требует сохранённого worktree и открытого Draft PR. Сторонние
локальные коммиты или изменения удалённой ветки останавливают работу для ручной
проверки истории; автоматическая синхронизация таких коммитов не выполняется.

Состояние находится в `runs_root/<repo-key>/<issue>/state.json`. Там же лежат
`report.json`, `report.md`, копия карточки и каталоги `attempt-*` с промптами,
результатами и журналами. Для planning, review и исправлений создаются отдельные каталоги.
Скрипт сохраняет проверенный Git-снимок, профиль, результаты review и историю
исправлений; обычный `run` продолжает незавершённый этап и не сбрасывает лимиты.
`--rerun` до коммита начинает новый цикл с текущим diff и сохраняет прежнюю
историю и расход токенов.

Версия workflow — `4`. Состояние версии `3` мигрирует без запуска моделей:
сохраняются исходная база PR, текущий коммит, результаты и журналы.
Новый цикл сохраняет предыдущую карточку и результат в `cycle_history`;
`cycle_base_sha` фиксирует начало доработки, `last_published_sha` — последний
опубликованный коммит. История циклов включается в отчёт.
Старые циклы, где coding уже запускался (включая неудачный
вызов), продолжаются без planning с причиной «цикл начат до добавления planning».
Их review, история и лимиты исправлений сохраняются. Если coding ещё не начинался,
planning включается до разработки. `--rerun` до коммита включает новый полный цикл.
Старый коммит без review требует завершения публикации вручную. Уже
опубликованные задачи возвращают существующий PR.

Отчёт показывает токены, расход лимита подписки, модели, глубину и результаты
по сессиям planning, coding, исправлений checks, review и исправлений review. Токены
читаются из `turn.completed.usage`: входные плюс выходные, кешированные
входные входят во входные. Проценты — оценка изменения общих лимитов аккаунта
за каждую сессию; параллельные задачи и задержки обновления влияют на неё.
Для исторических сессий без снимков лимитов процент неизвестен. При пропуске
review отчёт указывает «качество не оценивалось». Отчёт не добавляется в PR.

Пересчитать отчёт локально, в том числе для опубликованной APP-1:

```bash
./dev-task report android-tasks/APP-1/task.md --config config.json
```

Подробные команды и пути к журналам описаны в [WORKFLOW.md](WORKFLOW.md).

Результаты coding, check-fix и review-fix содержат `status`, `summary`,
`manual_checks`, `verification_limits` и `blockers`. `verification_limits` —
список проверок, которые агент не смог выполнить в своей песочнице, с причинами
(например, Gradle не смог открыть сокет). Завершённая реализация возвращает
`implemented` и пустой `blockers`, даже если есть такие ограничения. Статусы
`blocked` и `needs_input` требуют непустого `blockers`: это причины, мешающие
завершить реализацию, включая неустранённые ошибки обязательных checks скрипта.

После реализации dev-task сам запускает все `config.checks` в своём окружении.
Только их успех для текущего снимка разрешает review, commit и публикацию.
Ограничения проверок агента сохраняются отдельно в состоянии, отчётах и описании
PR; они не заменяют результаты обязательных checks. В старых сохранённых
результатах отсутствие `verification_limits` означает пустой список. Старые
`blockers` автоматически не переклассифицируются.

Если запуск остановился на coding из-за ограничения песочницы, повторите обычный
`run` с той же карточкой и конфигурацией: агент получит новый контракт результата
в существующем worktree. Редактировать историю и удалять worktree не требуется.

## Структура кода

Исполняемый файл `dev-task` передаёт управление в `dev_task.cli.main(argv=None)`.
Пакет лежит рядом со скриптом и не требует установки: запуск по абсолютному пути
работает из любого рабочего каталога.

| Модули пакета `dev_task` | Ответственность |
| --- | --- |
| `cli`, `workflow` | Аргументы и коды выхода; последовательность этапов и продолжение PR |
| `card`, `config`, `state` | Карточка; конфигурация и профили; миграции и история циклов |
| `planning`, `coding`, `checks`, `review`, `publishing` | Этапы workflow и принадлежащие им циклы исправлений |
| `plan_context`, `contracts` | Целостность плана и общий контекст; схемы, валидация и правила результатов |
| `codex`, `sessions` | Запуск Codex; учёт жизненного цикла сессии |
| `reports`, `usage` | Восстановление и формирование отчётов; токены и лимиты подписки |
| `repository`, `github`, `processes` | Git/worktree и снимки; GitHub CLI и PR; выполнение подпроцессов |
| `storage`, `errors`, `console` | Файловое хранение; исключения и проверка условий; вывод |

Зависимости направлены от `cli` к `workflow`, затем к этапам и инфраструктуре.
Этап review использует checks, checks — coding. Запуск модели использует цепочку
`codex → sessions → reports → usage`. Общие проверки Git-снимка находятся в
`repository`, проверка принятого плана — в `plan_context`, а правила результатов
review — в `contracts`. Благодаря этому публикация не импортирует этапы checks
или review. Нижние модули не импортируют `workflow` или `cli`.

Все импорты внутри пакета явные и находятся на уровне модуля. `__init__.py` не
реэкспортирует функции и не запускает код. Ограничения зависимостей и отсутствие
циклов проверяет `tests/test_architecture.py`.

Тесты актуального workflow используют локальный Git и подставные Codex/gh
с карточками KRMA/AAS:

```bash
python3 -m unittest discover -s tests -p test_check_repairs.py -v
python3 -m unittest discover -s tests -p test_usage_reports.py -v
python3 -m unittest discover -s tests -p test_code_review.py -v
python3 -m unittest discover -s tests -p test_planning.py -v
python3 -m unittest discover -s tests -p test_commit_messages.py -v
python3 -m unittest discover -s tests -p test_continue_pr.py -v
python3 -m unittest discover -s tests -p test_verification_limits.py -v
python3 -m unittest discover -s tests -p test_check_resume.py -v
python3 -m unittest discover -s tests -p test_architecture.py -v
python3 -m unittest discover -s tests -p test_cli.py -v
```

Исторический `test_workflow.py` относится к другой версии скрипта с иным форматом
состояния и префиксами KRMA/AAS.

### Путь к Android SDK

Необязательное поле `android_home` в `config.json` задаёт путь к SDK, например
`"android_home": "~/Library/Android/sdk"`. Скрипт раскрывает `~`, а относительный
путь разрешает от каталога конфигурации. Путь передаётся через `ANDROID_HOME`
всем дочерним командам, включая команды в worktree. Уже заданная переменная
`ANDROID_HOME` имеет приоритет. Без настройки используется текущее окружение.

## Review удалённой ветки

```bash
./dev-task review feature/APP-1234 --base develop --config config.json
```

Карточка не требуется. Обе ветки загружаются с `config.remote` (по умолчанию
`origin`); указывайте имена без префикса remote. Проверяется полный diff от
единственного merge-base до вершины проверяемой ветки. Каждый запуск получает
новый снимок удалённых веток и отдельный отчёт, без продолжения прошлого запуска.

Для review достаточно `repo`, `worktrees_root`, `runs_root`; `checks` и
`github_repo` необязательны. Нужны Git и авторизованный Codex CLI, `gh` не нужен.
Модель задаёт `review_profile`, по умолчанию `{"model": "astra", "effort": "low"}`;
поддерживаются aliases из `models`. Codex работает в `read-only`.
Setup, checks и автоматические исправления не запускаются.

Для непустого diff скрипт создаёт detached worktree вне основного checkout.
Основной checkout может содержать staged, unstaged и untracked изменения.
Локальные ветки и remote-tracking refs не обновляются. После завершения, ошибки
или прерывания чистый временный worktree удаляется; при наличии изменений,
включая ignored-файлы, сохраняется с выводом пути. Пустой diff не требует worktree
или вызова Codex.

Результаты, diff, SHA обеих веток и merge-base, журналы и расход сохраняются в
`runs_root/<repo-key>/reviews/<run-id>/`: `state.json`, `report.json`, `report.md`,
`review-context.json`, `review.diff`, а сессия — в `attempt-1/review-1/`.
Код выхода: `0` — нет P0/P1/P2 (или изменений), `1` — замечания либо ошибка,
`2` — неверные аргументы, `130` — прерывание. Детали причины находятся в отчёте.
