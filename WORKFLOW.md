# Запуск workflow для задачи

Команды выполняются из целевого Git-проекта или с `--project /path/to/project`.
По умолчанию конфигурация — `.dev-task/config.json` в Git-корне. Явные пути
карточки и `--config` считаются от каталога запуска. Старое `config.repo` игнорируется.

## 1. Подготовьте инструменты

Нужны Python 3.10+, Git, `gh` и авторизованный Codex CLI. Для Android-проекта
настройте JDK и SDK. Установите зависимость скрипта:

```bash
pipx install .
dev-task --help
```

В `.dev-task/config.json` целевого проекта укажите `github_repo`, корни `worktrees_root` и
`runs_root`, `setup`, обязательные `checks`, а также `allow_paths` и
`deny_paths`. Рабочие каталоги должны быть вне основного checkout. В
`codex_args` можно передать `--add-dir` для Gradle cache; planning и review работают в
`read-only` без дополнительного доступа на запись.

## 2. Создайте карточку
Скопируйте `examples/task.md` или заполните свою карточку:

```yaml
---
issue: APP-1234
base: develop
title: Редактирование имени пользователя
complexity: medium
---

Описание задачи и критерии приёмки.
```

Идентификатор задачи: `[A-Za-z0-9][A-Za-z0-9_-]*`; базовая ветка — любое корректное имя Git-ветки. Значения сложности: `trivial`,
`simple`, `medium`, `complex` (регистр не важен).

| Сложность | Planning | Coding и исправления | Review |
| --- | --- | --- | --- |
| trivial | пропуск | gpt-6-luna / low | пропуск |
| simple | пропуск | gpt-6-luna / medium | gpt-6.1-sol / low |
| medium | gpt-6.1-sol / medium | gpt-6.1-sol / medium | gpt-6-astra / low |
| complex | gpt-6-astra / high | gpt-6.1-sol / high | gpt-6-astra / medium |

В config.json можно задать профили ролей в `agents` и переопределить их для
конкретной сложности в `complexity_profiles`. Псевдонимы моделей задаются в `models`.
Значение `planning: null` или `review: null` пропускает соответствующий этап.
Модель не заменяется автоматически,
если она недоступна.

## 3. Запустите локально

```bash
dev-task run android-tasks/APP-1/task.md \
  --config config.json --local-only
```

Скрипт готовит отдельный worktree, выполняет setup, затем planning и coding
в отдельных сессиях Codex, после чего все checks. После них запускается review в другой сессии,
если он включён профилем. Review получает полный diff от исходного commit,
карточку и результаты checks; он не должен менять исходники.

Coding и исправления возвращают ограничения собственных проверок в
`verification_limits`, отдельно от `blockers` реализации. Например, запрет сокета
Gradle в песочнице не мешает передать завершённую реализацию (`implemented`,
пустой `blockers`) проверкам управляющего скрипта. Неустранённая ошибка checks
самого скрипта остаётся блокером. Review использует результаты скрипта и не должен
считать невозможность повторного запуска checks в read-only окружении блокером.
Все обязательные checks должны пройти для текущего снимка до дальнейших этапов.

После остановки на coding повторите ту же команду `run`: она заново вызовет агента
в существующем worktree. Старые блокеры не преобразуются автоматически;
отсутствующее в старом сохранённом результате `verification_limits` читается как
`[]`. Историю запусков вручную менять не нужно.

Planning работает в `read-only`: изучает проект и текущий diff, составляет план
изменений и проверок критериев приёмки. Скрипт сохраняет результат в
`attempt-*/planning-N/plan.md` вне worktree. Coding, review и исправления получают
путь к этому файлу. Его нельзя менять внутри цикла; потеря или изменение плана
требует `run --rerun` до коммита.

Проверьте staged diff в worktree, напечатанном командой:

```bash
git -C /путь/к/worktree diff --cached
```

Для отдельного запуска можно передать `--skip-planning` и/или `--skip-review`. Выбранный пропуск
сохраняется между обычными запусками. Изменения сложности, модели, глубины или
режима planning/review требуют `--rerun` до коммита.

## 4. Исправления

Ошибка, blocker, неверный JSON, таймаут или прерывание planning останавливают
работу до coding. Повторите обычный `run`: успешный setup не повторяется.
Если план уже успешно сохранён, после сбоя coding повторяется только coding
с тем же планом. Planning не повторяется в циклах исправлений checks/review.

При сбое checks или `git diff --cached --check` скрипт сохраняет журнал и
запускает исправление в новой сессии. После него все checks выполняются заново.
`max_check_fix_iterations` в config.json по умолчанию `3`; `0` отключает цикл.
Ошибки setup, изменения Git-состояния, запрещённые пути и изменения исходников
самими checks требуют ручного разбора.

Review возвращает замечания P0–P3. При P0/P1/P2 скрипт запускает исправление,
затем все checks и новое review. До трёх исправляющих сессий задаёт
`max_fix_iterations`; `0` отключает автоисправление. P3 сохраняются в отчёте,
но не требуют исправления. Лимиты checks и review независимы.

Ошибка, blocker, таймаут или прерывание Codex расходуют одну попытку
исправления. Повторите обычный `run`, чтобы продолжить в рамках оставшегося
лимита:

```bash
dev-task run android-tasks/APP-1/task.md \
  --config config.json --local-only
```

`--rerun` запускает новый цикл с текущим diff и сбрасывает лимиты исправлений,
сохраняя прежнюю историю и статистику. Его можно применить только до коммита.

При обновлении до версии workflow `3` старые циклы с уже запускавшимся coding
продолжаются без planning, сохраняя review, историю и лимиты. Если coding ещё
не начинался, planning включается. Новый цикл через `--rerun` использует всю
таблицу этапов. Уже опубликованная задача возвращает существующий PR.

## 5. Опубликуйте результат

```bash
dev-task publish android-tasks/APP-1/task.md --config config.json
```

`publish` использует сохранённое завершение/пропуск planning, повторяет checks и принимает только актуальное успешное review
проверенного Git-снимка либо сохранённый пропуск. При изменении кода выполните
`run`. После успешной проверки скрипт создаёт коммит, отправляет ветку и
открывает Draft PR. Повторный `publish` переиспользует существующий коммит.
Если коммит остановлен Git hook, устраните причину и повторите `publish` с той же
карточкой и конфигурацией, без `--rerun`. Сохранённое сообщение коммита используется
повторно для того же снимка. Вывод коммита и хуков сохраняется в
`attempt-*/commit.log`; путь печатается при запуске и в сообщении ошибки.
Если `core.hooksPath` указывает на абсолютный путь `<repo>/githooks`, при коммите
скрипт передаёт путь `<worktree>/githooks` через `git -c`. Общая конфигурация Git
не меняется, хуки выполняются. Остальные настройки `core.hooksPath` сохраняются.
Чтобы выполнить всё одной командой, запустите `run` без `--local-only`.

Для доработки опубликованного Draft PR измените карточку и запустите:

```bash
ANDROID_HOME="$HOME/Library/Android/sdk" dev-task run android-tasks/KRMA-10003-add-username-validation-error/task.md \
  --config config.json --continue-pr
```

Версия workflow `4` автоматически мигрирует состояние версии `3`. Продолжение
сохраняет незакоммиченные изменения и выполняет новый цикл в прежнем worktree.
Новый коммит отправляется в ту же ветку; заголовок и описание PR сохраняются.
Review видит полный diff PR, сообщение коммита описывает текущую доработку.
Если нового diff нет, цикл завершается без пустого коммита.

Для локального результата добавьте `--local-only`, затем выполните `publish`.
После ошибки повторите `run` или `run --continue-pr`: попытки не сбросятся.
После ошибки push повторите `publish`: коммит не будет создан повторно.
Если карточка изменилась в активном цикле до коммита, используйте `run --rerun`;
после коммита сначала завершите публикацию с прежней карточкой.
`--continue-pr` несовместим с `--rerun`. Поля `issue` и `base` неизменяемы.
Сторонние коммиты, изменение удалённой ветки, отсутствие PR или выход PR из
состояния открытого Draft останавливают продолжение для ручной проверки.

## 6. Посмотрите отчёт и журналы

```bash
dev-task report android-tasks/APP-1/task.md --config config.json
```

Эта команда восстанавливает отчёт из локальных журналов, не запуская модель,
checks или публикацию. Она работает и для опубликованной задачи. В
`runs_root/<repo-key>/<issue>/` находятся `state.json`, `report.json`,
`report.md` и каталоги `attempt-*`. Каждая сессия содержит `events.jsonl`,
`codex.stderr.log`, `result.json`, промпт и `usage.json`. Каталоги review
также содержат полный проверенный diff и контекст checks; исправления — файл
замечаний или сбоя checks.

Каталог `attempt-*/planning-N/` содержит `plan.md`, структурированный результат,
`planning.json` с итогом сессии и снимок `snapshot-before.json`. В `state.json`
сохраняются завершение setup, состояние planning, контрольная сумма плана и
признак начала coding. `report` показывает историю planning по циклам и ссылки
на все сохранённые планы.

Отчёт показывает токены, модели, глубину, итог review, замечания и число
исправлений по каждому этапу и циклу. Кешированные входные токены входят в
число входных и повторно не прибавляются. Процент лимита подписки оценивается
по изменению показателя аккаунта за время сессии. При сбросе окна, недоступности
показателей или для старых запусков без снимков процент неизвестен. Пропуск
review означает «качество не оценивалось».

Полный набор запускается через `python3 -m unittest discover -s tests`.
Исторический класс `test_workflow.WorkflowTest` ожидает старый формат отчётов
и состояния; актуальные интеграционные проверки используют остальные классы.

## Review удалённой ветки

```bash
dev-task review feature/APP-1234 --base develop --config config.json
```

Карточка не требуется. Обе ветки загружаются с `config.remote` (по умолчанию
`origin`); указывайте имена без префикса remote. Проверяется полный diff от
единственного merge-base до вершины проверяемой ветки. Каждый запуск получает
новый снимок удалённых веток и отдельный отчёт, без продолжения прошлого запуска.

Для review достаточно `worktrees_root`, `runs_root`; `checks` и
`github_repo` необязательны. Нужны Git и авторизованный Codex CLI, `gh` не нужен.
Приоритет имеет `review_profile`, затем применяется `agents.review`.
Профиль по умолчанию — `{"model": "astra", "effort": "low"}`. Codex работает в `read-only`.
Setup, checks и автоматические исправления не запускаются.

Для непустого diff скрипт создаёт detached worktree вне основного checkout.
Основной checkout может содержать staged, unstaged и untracked изменения.
Локальные ветки и remote-tracking refs не обновляются. После завершения, ошибки
или прерывания чистый временный worktree удаляется; при наличии изменений,
включая ignored-файлы, сохраняется с выводом пути. Пустой diff не требует worktree
или вызова Codex.

Результаты, diff, SHA обеих веток и merge-base, журналы и расход сохраняются в
`runs_root/<repo-key>/reviews/<run-id>/`: `state.json`, `report.json`, `report.md`,
`review-context.json`, `review.diff`, а сессия — в `attempt-1/review-1/`.
Код выхода: `0` — нет P0/P1/P2 (или изменений), `1` — замечания либо ошибка,
`2` — неверные аргументы, `130` — прерывание. Детали причины находятся в отчёте.
